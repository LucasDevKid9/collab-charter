# 深度分析：四份材料的能力、缺陷与融合机会

> 分析对象
> 1. `superpowers` v7.0.0（231 文件，Jesse Vincent，MIT）—— Agent 技能框架
> 2. `cognitive-core` v3.1（5 文件）—— 七层认知引擎 Skill
> 3. `模块化特征簇标记语法·创作范式与协作规范总纲` V1.0（302 段/7 表）—— 图像提示词创作范式
> 4. `用户协作宪章` v3.1（自有文档，11 章）—— 用户侧跨 AI 协作规范
>
> 方法：**实证复现式**，不满足于静态阅读——每一条"缺陷"都尽量给出可复现的判定；
> 每一条"优点"都尽量指出它为什么在机制上成立。

---

## 一、四份材料的定位

| 材料 | 层级 | 它真正解决的问题 | 它没解决的问题 |
|---|---|---|---|
| superpowers | **框架层** | 技能如何被写出来、被发现、被多平台投递 | 与具体领域无关，不含协作规范与视觉知识 |
| cognitive-core | **认知层** | 一次任务内部该怎么想、怎么查、怎么自证 | 结构扁平，无代码、无接口、无校验、不可被调用 |
| 特征簇总纲 | **领域层** | 图像提示词该怎么分解、评估、优化 | **纯文档**，第 12.2 节预留的五个模块全部未实现 |
| 用户协作宪章 | **规范层** | 用户与任意 AI 协作时应遵守什么 | 只有"应该"，没有"如何执行"；无路由、无裁决、无自检的实现 |

四者**不重叠、可正交组合**：规范层定"对错"，框架层定"如何承载"，认知层定"如何思考"，
领域层定"具体怎么做"。

## 二、逐份材料的缺陷清单

### A. superpowers v7.0.0

**结论：作为框架近乎无可指摘，本项目的架构大量借鉴它。** 但存在两处可讨论点。

| 级别 | 问题 | 判定依据 | 本项目的处理 |
|---|---|---|---|
| P2 | 体量导致"仪式感"风险：14 个平台 × 15 个技能的投递面很大，对轻量任务可能过重 | `AGENTS.md` 自己承认"skill 内容按真实代理行为大量调优"，说明维护成本高 | 只吸收其**三层投递模型**（技能/映射/引导），不复制其技能数量 |
| P3 | `hooks/session-start` 的平台分支靠环境变量嗅探（`CURSOR_PLUGIN_ROOT` / `CLAUDE_PLUGIN_ROOT` / `MUSE_PLUGIN_ROOT`），新增平台需改脚本 | 脚本第 90–105 行 | 保留该设计（务实），但在 `tool-mapping.md` 里显式记录，避免"改了不知道要改哪" |

**值得吸收的机制（本项目已采用）**：

1. **动作词汇 + 平台映射表**：技能正文永不指名工具，平台差异收敛到一张映射表。
   这是"一份技能跑遍所有平台"的唯一可行解。
2. **技能发现优化（SDO）**：description 只写触发条件、**绝不概述流程**——因为概述
   会制造捷径，让代理照着 description 干而不读正文。本项目全部技能遵守。
3. **形式匹配失败类型**：禁令式对"违规"有效，对"形状错误"会**反噬**。这是罕见的
   有实测支撑的写作指导，已写入 `authoring-skills`。
4. **"违反字面即违反精神"**：一句切断整类合理化。
5. **零依赖设计**：`AGENTS.md` 明写 "Superpowers is a zero-dependency plugin by design"。
   本项目的 MCP server 因此也不依赖 `mcp` SDK。

### B. cognitive-core v3.1

**结论：内容有真价值，但工程形态不合格——它是一份"说明"，不是一个"能力"。**

| 级别 | 问题 | 判定依据 | 本项目的处理 |
|---|---|---|---|
| **P0** | **不可调用**：没有可执行入口、没有工具定义、没有 schema。任何 Agent 想用它，只能整份读进上下文 | 全仓库仅 5 个 `.md`，无 `.py`/`.json`/`.toml` | 转化为 MCP 工具 + CLI，检索与校验部分代码化 |
| **P0** | **描述与内容脱节**：frontmatter description 列举能力（七层架构+色彩+Prompt工程），属于 superpowers 明令禁止的"概述流程" | `SKILL.md` 第 3 行；对照 superpowers 的 SDO 规范 | 重写为纯触发条件 |
| **P1** | **结构扁平**：1 个主文件承载 7 层架构，全部细节平铺；`references/` 只有 3 个文件且与主文件职责重叠 | 主文件行数远超"重参考应拆分"的门槛 | 按"主文件精简 + 分层引用"重构 |
| **P1** | **无可验证性**：声称"证据优先""交叉验证"，但没有任何机制强制它发生 | 全篇是祈使句，无断言、无检查表、无失败条件 | 证据链与三态结论转化为 `deep-research` 的**可判定步骤** |
| P2 | **信源分级与三态标注**设计良好但未被固化 | 第 3 层"阶段 3" | 完整保留进 `deep-research` 技能，作为该技能的核心价值 |
| P2 | 七层架构中"输出引擎（第 7 层）"与"分析引擎（第 5 层）"职责有重叠 | 第 5 层含"输出范式"，第 7 层又是"输出引擎" | 合并为单一"输出过滤"概念，对齐宪章 0.7 |

**值得吸收的内容（本项目已采用）**：
五阶索引协议、信源 A/B/C/D 分级、**对抗性搜索清单**（主动找反例，而非只找支持证据）、
三态结论（✅已验证 / 🟡待验证 / ⚔️存在争议）、证据溯源账本 `[E1][E2]`、三种输出模式自适应。

### C. 特征簇标记语法总纲 V1.0

**结论：理论完整度最高的一份，但**它自己承认了最大的缺陷**——第 12.2 节列出的
五个"可插入模块"，本质上是五张代码规格书，而一个都没实现。**

| 级别 | 问题 | 判定依据 | 本项目的处理 |
|---|---|---|---|
| **P0** | **规范无执行载体**：第 9 章的标记语法（`(词条:1.2)`、`[簇名称]`）需要解析器才能被机器处理；第 5.4 节"控制力量化"需要评分器；第 11 章十条禁止需要 linter。全部缺失 | 全文档无一行代码 | 实现 `tools/fcslint`（解析器 + 9 条规则 + 评分器 + 优化建议器） |
| **P0** | **第 12.2 节五个预留模块全部为空** | 规范自述"预留模块化插入位…供…调用" | 风险量化矩阵 → `FCS006`+`FCS009`；权重梯度表 → `lexicon.yaml:weight_gradient`；冲突类型库 → `direct_conflicts`/`cross_domain_conflicts`；实证反馈回路 → `memory` 模块；参考图反向工程 → 接口位预留 |
| **P1** | **术语存在未定义的口径**：3.5 说"顺序即隐性权重"，11 章说"禁止默认所有逗号词条权重均等"，但未规定二者冲突时如何裁定 | 第 3.5 与第 11 章 | 实现为 `FCS010`（info 级提示，非判决），并在 `conflict-rules.md` 明确"权重优先，但主体锚点顺序不得后移" |
| **P1** | **"离链词条"只有判定没有清单**：6.1 要求词条必须能归属链路环节，但未给出可查表 | 第 6.1 节 | 在 `lexicon.yaml` 的 `chain_stages` + 每条词条的 `chain` 字段落实 |
| P2 | 附录 B「对外对齐协议」说"在六轮对话内完成范式对齐"，但未给出可验收的中间产物 | 附录 B | 转化为 `charter_receipt` + `using-charter` 技能：首次响应即产出可执行清单 |
| P2 | 案例库的"深度解读"与正文规则有轻微不一致（如案例一把 `近窥视随手拍` 与 `抠图伪影` 判为异源，但未指明依据 6.1 的哪一环） | 附录 A.1 | 在 `cases.md` 中补齐链路环节归属 |

**值得吸收的内容（本项目已采用）**：六大功能簇封闭集、四层设计模型、媒介链路溯源法、
直接冲突与跨域冲突的**二分处理**（删 vs 标记）、三大分支类型与跨分支转换、
词条类型学（实体/抽象/技术参数）、"实例可变，体系恒常"的核心认知。

### D. 用户协作宪章 v3.1

**结论：设计质量很高——尤其第〇章"信息流协议"把散落的规则统一成了一个运行时。
但它同样停留在"应该"层面。**

| 级别 | 问题 | 判定依据 | 本项目的处理 |
|---|---|---|---|
| **P0** | **路由管线无实现**：0.3 定义了八站，但没有任何东西保证它被执行 | 0.3 是文本描述 | `Router` 类实现八站，并用一条断言把"站点集合"锁死在宪章上（改宪章不改代码会直接报错） |
| **P0** | **裁决规则无实现**：0.4 五级优先级、0.5 五条冲突规则，冲突时谁让位全靠模型临场判断 | 0.4 / 0.5 | `Arbiter` 类实现，每条裁决结论都带 clause 字段可回溯 |
| **P0** | **安全闸门无实现**：0.2 的"敏感度 × 权限"驱动闸门，但矩阵从未被写出 | 0.2 / 第十章 | `charter.yaml:enforcement.gate_matrix` 补齐 3×3 全组合，`SafetyGate` 执行；未覆盖组合按最保守处理并显式说明 |
| **P1** | **0.8 自检不可判定**：六项自检都是疑问句，没有通过/失败标准 | 0.8 | 每个检查项返回可断言的 `passed` 布尔值 + 失败详情 |
| **P1** | **0.6 记忆流缺少时效的具体参数**："置信度随时效衰减"未给半衰期 | 0.6-O3 | 在 `memory.py` 显式定义半衰期（实时 1h / 会话内 7d / 长期稳定不衰减） |
| **P2** | 0.9 快速通道的条件与第二章"用户画像"存在张力（既要轻量又要求对齐） | 0.9 vs 第二章 | 用可判定谓词实现：L1 或"快速"走最小管线，创造性/多步/本地文件强制全量 |
| P2 | 第九章快捷词无 id，无法被程序引用 | 第九章 | 补 `9-W1`…`9-W6` 条款 id，纳入追溯体系 |

## 三、融合后的能力缺口（本项目的立项理由）

四份材料合起来，**缺的只有一件事：执行层**。

```
用户协作宪章      说"应该怎样"        → 缺：跑起来
特征簇总纲        说"这样才对"        → 缺：能验证
cognitive-core    说"这样想"          → 缺：能被调用
superpowers       说"技能该这么写"    → 缺：与上述三者无关
──────────────────────────────────────────────────
缺的那一层 = 可加载 + 可调用 + 可验证的执行层
```

于是有了 `collab-charter`：**宪章层（规范）→ 内核层（执行）→ 接口层（调用）→
技能层（承载）→ 适配层（投递）→ 验证层（追溯）**。六层全部有实际文件落地，
见 [ARCHITECTURE.md](ARCHITECTURE.md)。

## 四、本项目的自我约束（避免重蹈覆辙）

分析完四份材料，本项目给自己定了四条不可违反的规则：

| # | 规则 | 防止的失败 |
|---|---|---|
| 1 | **单一事实源**：条款只写在 `charter/charter.yaml`，代码与文档都引用它 | cognitive-core 的"描述与内容脱节" |
| 2 | **条款可追溯**：每条条款有 id，每项实现申报它执行哪些条款，测试反向验证 | 特征簇总纲的"规范无执行载体" |
| 3 | **形式匹配失败**：违规用禁令，形状错误用配方，漏项用槽位 | superpowers 记录的"禁令对形状问题反噬" |
| 4 | **技能平台无关**：正文只写动作，平台差异进映射表 | cognitive-core 的"不可跨平台调用" |

## 五、仍未解决的问题（如实标注，不掩盖）

| 问题 | 状态 | 原因 |
|---|---|---|
| 词库覆盖率有限（约 150 条） | 待补 | 依据 6.6，新词必须由人判定并给理由，不能由程序猜测；工具遇到 `FCS001` 会显式报出而非静默过滤 |
| 参考图反向工程模块 | 仅留接口位 | 依据 12.2，该模块需要视觉模型能力，超出纯文本内核的边界 |
| "顺序 vs 权重"冲突的最终裁定规则 | 已给建议未给判决 | 规范本身未定义；本项目按"权重优先但主体锚点顺序不得后移"实现为提示（`FCS010`），避免越权替创作者决定 |
| 子代理并行的真实并行度 | 依赖宿主 | 宪章 7-R3 的三角视角在无子代理能力的平台上只能串行；`tool-mapping.md` 已登记降级方案 |

> 依据宪章 **5-R2 / 8-R2**：无可靠依据时标注"待验证"，不以印象代替判断。
